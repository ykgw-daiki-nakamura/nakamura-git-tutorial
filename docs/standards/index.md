# 概要・基本方針

本セクションは、この製品の開発規約をまとめる。ブランチの切り方とマージの仕方、出荷するバージョンの作り方、環境へのデプロイ、障害が起きたときの動き方、依存パッケージの取り込み方、顧客ごとの差分の扱い方を定める。

## 基本方針

規約は次の 5 つの問いに答える形で組み立てている。日々の開発で直接効くのは 1 と 4、リリースのときに効くのが 2 と 3、依存を追加・更新するときに効くのが 5 である。

### 1. どこで開発するか — main 1 本に統合する

**規約**: `main` を唯一の統合ブランチとし、long-lived な開発ブランチを作らない。これに出荷・保守のための `release/vX.Y` を足した形を採用する。[GitHub Flow](../guide/github-flow) にリリースブランチを足したもので、[GitLab Flow](../guide/other-flows#gitlab-flow) のリリースブランチ版にあたる。

**一言でいうと**: 作業ブランチは `main` から切り、`main` へ戻す。それだけである。`develop` のような 2 本目の統合ブランチは作らず、`release/vX.Y` も開発の場ではない（出荷したバージョンを保守するための枝である）。

**なぜ**: 統合先が 1 本なら、変更は 1 回マージすれば全員に届く。統合先が増えるほど、同じ変更を複数の経路へ流す手間と、流し忘れによるブランチ間の差が増える。

### 2. 何を出荷するか — main の先頭ではなくタグ

**規約**: 出荷する成果物は、`release/vX.Y` ブランチ上のコミットに打ったタグ（= GitHub Release）からビルドする。`main` から継続デプロイはせず、リリース単位でバージョンアップする。

**一言でいうと**: `main` の先頭は「次に出すバージョンの作りかけ」であって、出荷物ではない。出荷物には必ず `v1.2.0` のようなタグが付いていて、名前で呼べる。

**なぜ**: 障害調査や脆弱性対応で最初に必要になるのは、いま動いているコードがどのバージョンかの特定である。出荷の起点をタグに絞れば、これがタグ 1 つで決まる。

### 3. どこへ配るか — 環境はブランチで表さない

**規約**: 環境（`dev` / `staging` / `production`）は **GitHub Environments とデプロイパイプライン**で表現する。環境ブランチ（`develop`・`staging`・`production` といった、環境名を付けた常設ブランチ）は作成しない。

**一言でいうと**: ブランチが表すのはバージョンの系列だけである（`main` は次期バージョン、`release/v1.2` は v1.2 系）。どの環境で何が動いているかは、ブランチではなくデプロイの記録が持つ。

**なぜ**: 環境をブランチで表すと、1 つの修正を環境の数だけマージして回ることになる。流し忘れた環境だけが古いまま取り残され、環境間の差として残り続ける。

### 4. 修正はどう流れるか — main が先、release へは cherry-pick

**規約**: すべての修正はまず `main` に取り込み、必要なものだけを `release/*` へ cherry-pick する。逆方向のマージは禁止する（upstream first）。

**一言でいうと**: 出荷済みバージョンで見つかったバグでも、直す場所は `main` である。`release/*` は修正を受け取るだけで、`main` へ送り返さない。

**なぜ**: release 側で直して `main` へ戻し忘れると、次のバージョンで同じバグが再発する。流れを一方向に固定すれば、この戻し忘れという失敗の形自体が無くなる。

### 5. 何から守るか — サプライチェーンは多層で守る

**規約**: 依存の取り込みを遅らせ、インストール時のコード実行を許さず、既知の脆弱性を CI で検知する。

**一言でいうと**: 1 つの対策で防ぎ切るのではなく、層を重ねて前の層の取りこぼしを次の層で受ける。

**なぜ**: どの層も単独では破られる前提に立つ。取り込みを遅らせる対策は推移的依存に効かず、既知の脆弱性の検知は公開直後の悪性パッケージに効かない。

## 規約の担保

以降の各ページが定める規約は、担保のされ方が一様ではない。GitHub の設定やワークフローが**強制**するもの、**検知のみ**するもの、人の**運用**に委ねるものが混在する。どの規約がどれにあたるかは[規約の担保状況](./enforcement)に一覧としてまとめる。
