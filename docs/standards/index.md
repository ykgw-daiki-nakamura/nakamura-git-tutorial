# 概要・基本方針

本セクションは、この製品の開発規約をまとめる。

## 目的と基本方針

本規約は、SaaS 版とセルフホスト版を単一コードベース・**同一バージョン**で提供するための運用を定める。対象は、ブランチ運用とリリース・デプロイ、そこへ流入する依存とビルド経路の防御、出荷後の障害対応、および顧客別カスタマイズの進め方である。

基本方針は次のとおり。

1. **GitLab Flow（リリースブランチ版）**: [GitHub Flow](../guide/github-flow) を土台に、`main` を唯一の統合ブランチとし、long-lived な開発ブランチを作らない。これに出荷・保守のための `release/vX.Y` を足した形（= [GitLab Flow](../guide/other-flows#gitlab-flow) のリリースブランチ版）を採用する。
2. **タグ起点のリリース**: SaaS 版・セルフホスト版ともに、`release/vX.Y` ブランチ上のタグ（= GitHub Release）からビルドされた成果物を出荷する。SaaS 版も `main` から継続デプロイはせず、リリース単位でバージョンアップする。
3. **ブランチはバージョン系統、環境はデプロイ状態**: 環境（dev / staging / production）は **GitHub Environments とデプロイパイプライン**で表現する。環境ブランチは作成しない。
4. **upstream first**: すべての修正はまず `main` に取り込み、必要に応じて `release/*` へ cherry-pick する。逆方向のマージは禁止する。
5. **サプライチェーンは多層で守る**: 依存の取り込みを遅らせ、インストール時のコード実行を許さず、既知の脆弱性を CI で検知する。どの層も単独では破られる前提に立つ。

## 開発者の要点

前節は規約全体の設計方針である。日々 `main` へ PR を出す立場で守るのは、次の 5 点に集約される。詳細と根拠は各ページに定める。

1. **ブランチは 4 種類だけ**。`main` / feature / fix / `release/vX.Y` とし、環境ブランチ（`develop` / `staging` 等）は作らない。feature / fix の名前は課題管理ツールの既定名でよいが、課題番号は必ず含める。`main` は次期バージョンの開発ラインであり、出荷の起点にはしない（[ブランチ運用](./branching)・[禁止事項](./anti-patterns)）。
2. **修正は必ず `main` から始める**。出荷済みバージョンで見つかったバグでも、まず `main` に入れてから `release/*` へ cherry-pick する。`release/*` で直して `main` へ戻すマージも、`main` → `release/*` の merge / rebase も禁止する（[ブランチ運用](./branching)・[マージルール](./merge-rules#マージルール)）。
3. **PR タイトルは 2 か所に残る**。squash merge のため、PR タイトルがそのまま `main` のコミットメッセージになり、同時に自動生成されるリリースノートの見出しになる。Conventional Commits に準拠させ（書式は CI が検証する）、`修正` のような内容を持たない要約は書かない（[PR タイトル規約](./merge-rules#pr-タイトル規約)・[リリースとデプロイ](./release#github-release-運用規約)）。
4. **未完成でもブランチに溜めない**。long-lived な feature ブランチは作らず、作りかけの機能は dark launch / 非公開 API としての先行マージ / branch by abstraction のいずれかで到達不能にして `main` へ入れ、どの手段で隔離したかを PR 本文に書く。いずれもビルド時の隔離であり、実行時に稼働中の機能を切り離す用途には使えない（[導入までの暫定規約](./versioning#導入までの暫定規約)）。
5. **`main` へのマージには条件がある**。PR 経由であること・1 名以上の承認・承認後の push による承認の失効・CI の成功・レビューコメントの解決・linear history。いずれも Repository Rulesets が強制するため、満たすまでマージできない（[ブランチ保護](./branch-protection)）。

### リリース・障害の場面で効く規約

日々の PR では現れないが、出荷とその後で効くものを挙げる。

- **出荷はタグから、ビルドは 1 回だけ**。RC タグ（`vX.Y.Z-rc.N`）の push でビルドし、GA タグ（`vX.Y.Z`）では再ビルドせず RC 成果物を昇格させる。`main` から本番へ直接デプロイする経路は無い（[リリースとデプロイ](./release)）。
- **障害対応はロールフォワードが第 1 選択**。ロールバックは修正リリースの見込みが立たない場合の限定手段であり、可否は DB マイグレーションの互換性（expand-contract）で決まる（[障害対応](./incident)）。
- **セルフホストのアップグレードは MINOR を飛ばさない**。expand-contract が保証するのは隣接バージョン間の互換性だけである（[セルフホスト版のアップグレードパス](./versioning#セルフホスト版のアップグレードパス)）。
- **依存は多層で守る**。lockfile の固定・公開直後のバージョンを寝かせる cooldown・インストール時スクリプトの無効化・脆弱性の 2 層検知を重ね、GitHub Actions はコミット SHA でピン留めする（[依存とサプライチェーン](./supply-chain)）。

> **検討中のページを参照している箇所**
>
> 上の要点 4 と「MINOR を飛ばさない」の参照先である[バージョン運用](./versioning)は検討中（🚧）であり、記載は確定規約ではない。運用の根拠として参照しないこと。

判断に迷ったら[禁止事項](./anti-patterns)を見る。「禁止事項 / 理由 / 代わりに」の 3 列で並べてあり、何が駄目でどうすればよいかが最短で分かる。用語の定義は[用語と背景](./glossary)にまとめる。

## 規約の担保

以降の各ページが定める規約は、担保のされ方が一様ではない。GitHub の設定やワークフローが**強制**するもの、**検知のみ**するもの、人の**運用**に委ねるものが混在する。どの規約がどれにあたるかは[規約の担保状況](./enforcement)に一覧としてまとめる。
